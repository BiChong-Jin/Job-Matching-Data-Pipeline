# Job Matching Data Pipe Line

BigQueryとdbtを基盤としたイベント駆動型分析パイプラインです。
求人マッチングのユーザーイベントをRawレイヤーに取り込み、
正規化・重複排除されたイベントに変換し、さらにファネル、ランキング品質、
A/Bテスト結果などのビジネス向けメトリクスに集約します。

このプロジェクトは、データウェアハウス中心のパイプライン設計、
インクリメンタル変換、データ品質テストを実演しています。

## 時系列ワークフロー

```
T0 (終日)
└─ ユーザーが求人検索・ランキングを利用

T1 (夜間バッチ)
└─ バッチジョブがRawイベントを書き込み
   → job_matching_bronze.events_raw

T2 (取り込み後)
└─ dbt run --select silver
   → job_matching_silver.events

T3 (silver完了後)
└─ dbt run --select gold
   → job_matching_gold.*

T4 (翌朝)
└─ PM / エンジニアがダッシュボードとメトリクスを確認
```

## 課題と学び

### 1. BigQueryストリーミングインサートの制限（無料枠）

問題

初期の取り込みではPythonクライアント経由でBigQueryストリーミングインサートを使用していました。しかし、無料枠ではストリーミングインサートが許可されていないため、失敗しました。

解決策

バッチ指向の取り込みアプローチに切り替えました：

- ローカルでNDJSONファイルを生成
- BigQueryロードジョブをプログラムで実行してデータをロード
- 再処理可能性とコスト効率を維持

学び

バッチロードジョブは、信頼性、コスト管理、再処理の観点から優れており、本番システムで広く使用されています。

### 2. dbtプロファイルとスキーマ設定の落とし穴

問題

profiles.ymlのdatasetと+schemaモデル設定の相互作用により、dbtが予期しないデータセット名（スキーマが連結されるなど）を生成しました。

解決策

- profiles.ymlに中立的なdataset（dbt）を設定
- モデルグループ（silver、gold）ごとに+schemaを使用して出力データセットを明示的に制御
- dbtアーティファクトをクリーンアップしてモデルを再コンパイル

学び

dbt-bigqueryでは、プロファイルのdatasetとモデルのschema設定が密接に関連しています。明確な分離により命名の曖昧さを回避できます。

### 3. dbtモデルのSQLコンパイルエラー

問題

SQLファイルの末尾にセミコロンがあったため、dbtモデル実行時にBigQueryが構文エラーを発生させました。

解決策

- dbtモデルのSQLから末尾のセミコロンを削除
- dbtの内部クエリラッピング（CREATE TABLE AS SELECT）に依存

学び

dbtモデルは単一の有効なSELECT文を含む必要があります。テンプレート環境では、わずかなSQL構文の違いが重要です。

### 4. dbtのビルド状態とキャッシュの理解

問題

設定の変更がdbtの実行にすぐに反映されませんでした。

解決策

- dbt cleanを使用してコンパイル済みアーティファクトとキャッシュされたマニフェストを削除
- クリーンな状態でdbtを再実行

学び

dbtはコンパイルアーティファクトをローカルにキャッシュします。設定や環境の変更後はクリーンアップが必須です。
